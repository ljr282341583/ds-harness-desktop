# 2026-09-24 应用内更新"激活后秒回退"bug 与手工激活 0.1.7-rc.2

> 会话类型：问题诊断 + 手工绕过。**未改任何代码**，只改了运行时状态文件。
> 环境：B机（全机安装，程序在 `D:\AI(CODEX)\dsh desktop\DS Harness Desktop`）

## 现象

用户在托盘切到 `preview` 通道后更新 dsh，界面提示"重启后生效"，**重启完仍是 0.1.5**。

## 结论：不是 dsh 的问题，是桌面壳的 bug；且该功能从未成功过

日志 `%APPDATA%\ds-harness-desktop\dsh-desktop.log` 原文（2026-09-24）：

```
14:48:19  [updater] 更新通道 → preview
14:52:41  install: 完成 v0.1.7-rc.2（integrity=sha512-SQFhriLv...）
14:53:17  smoke: 通过 http://127.0.0.1:3199/?token=...      ← 冒烟验证通过
14:53:17  [updater] 激活 v0.1.7-rc.2，重启服务               ← 已激活
14:53:17  dsh child exited: code= null signal= SIGTERM      ← 旧子进程被杀
14:53:17  [updater] 覆盖版本启动失败，回退内置版本： 0.1.7-rc.2  ← 1ms 后误判回退
14:53:19  startHarness: ... bin= ...\resources\app\node_modules\@deepseek-ai\dsh\lib\bin.js
```

下载 ✓ 安装 ✓ 冒烟 ✓ 激活 ✓ —— 然后 **1 毫秒内**被判定"启动失败"并回退。1ms 连进程都 spawn 不出来。

### 根因：旧子进程的 exit 事件被误算到新版本头上（陈旧退出竞态）

`app/src/main.js` 更新流程：

```js
772:  const result = await updater.updateToLatest({...});  // 内部 activate() → activeVersion 已写上
788:  stopHarness();                                       // 杀旧的内置版子进程
790:  await startHarness();                                // 才轮到用覆盖版启动
```

而 `startHarness()` 的退出回调（473-495 行）**不区分死的是哪个子进程**：

```js
child.on('exit', (code, signal) => {
  dshChild = null;
  if (quitting) return;
  const overrideState = updater.readState(updateBaseDir());
  if (overrideState.activeVersion && !overrideFallbackDone) {
    log('[updater] 覆盖版本启动失败，回退内置版本：', ...);   // ← 误判点
    updater.deactivate(updateBaseDir());
```

顺序成死结：**先激活**（activeVersion 有值）→ **再杀旧进程** → 旧进程 exit 迟到 → 回调读到 activeVersion 有值，认定新版启动失败 → 回退。
19.644 / 19.652 两次 `startHarness` 用的都是**内置版路径** → 0.1.7 **从未被拉起过一次**；回退分支与更新流程各调一次，还在 3080 上并发起了两个进程。

### 影响面：这功能从来没成功过一次

同样"激活→秒回退"共 4 次：09-12、09-20（两次）升 `0.1.5-rc.2`，09-24 升 `0.1.7-rc.2`。
`state.json` 的 `previousVersion` 字段**不是**成功记录，别误读（本次会话一度误读并得出错误结论，已更正）。

## 本次所做（路线 A：手工绕过）

1. **备份 `~/.dsh`** → `C:\Users\Administrator\.dsh.bak-20260924-230423`
   - 13186 个文件全部复制、0 失败；107 个目录报错 = `profiles\node_modules` 下的 **junction**（指向项目 dev 树，非用户数据，可重建）
   - 关键数据核对一致：sessions 112 个 / 72.7 MB、storages 163 个、skills 13 个、`.credentials.yaml` / `settings.yaml` 字节数完全相同
2. **改 `%APPDATA%\ds-harness-desktop\dsh-update\state.json`**（原文件已备份为同目录 `state.json.bak-20260924-230555`）：

```json
{ "activeVersion": "0.1.7-rc.2", "channel": "preview",
  "previousVersion": "0.1.5-rc.2", "lastResult": "activated" }
```

写入用 `[Text.UTF8Encoding]::new($false)`，**无 BOM**（`JSON.parse` 遇 BOM 会抛）。

3. **用壳自己的 `updater.js` 验证**（bundled `node.exe`，非推断）：

```
readState         = {"activeVersion":"0.1.7-rc.2", ...}
resolveActiveRoot = ...\dsh-update\versions\0.1.7-rc.2
覆盖版本 dsh 版本  = 0.1.7-rc.2
bin.js 存在       = true
兼容守卫          = {"ok":true,"reason":null}
```

冷启动安全的前提（已在代码中核实）：
- `cleanup()` 只在 `updateToLatest` 内调用，**冷启动不会删版本目录**
- bootstrap 唯一回退点（150-153 行）只在 `resolveActiveRoot()` 返回 null 时 deactivate → 上面已验证非 null
- 托盘「退出」置 `quitting=true` → 回调提前 return，**不会**改写 state.json；无退出钩子覆盖

## ⚠️ 使用约束

- **必须"完全退出壳再重开"**（托盘 → 退出）。
- **绝不能点托盘「重启服务」**：那走 `stopHarness()` + `startHarness()`，踩同一竞态，当场打回 0.1.5。
- 重开前**别碰**「检查 dsh 更新」和通道切换（会重写 state.json）。
