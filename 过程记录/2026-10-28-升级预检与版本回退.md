# 2026-10-28 · 升级预检 + 一键版本回退 + profile 体检

> 触发：dsh 引擎从 0.2.0-rc.2 升到 0.2.1-rc.4 后应用起不来，用户手动改 `state.json` 才恢复。
> 本轮补的是一条闭环：**装完先预检 → 不通过不激活 → 出错能一键退回上一版本**。

## 一、事故根因（不是引擎 bug，也不是壳 bug）

- `dsh-child.log` 原文：
  `dsh: disabling profile plugin row "tools": Plugin @deepseek-ai/dsh-tools@0.2.0-rc.2 is incompatible with dsh 0.2.1-rc.4: requirements {"@deepseek-ai/dsh-agent":"0.2.0-rc.2", …}`
  → `dsh: startup failed: 1 required plugin did not activate`
- 成因链：本地插件（`dsh-orb`、`dsh-project-ledger`）把 `@deepseek-ai/dsh-tools` 写在
  `dependencies` 且钉死精确版本 → pnpm 在 profile 里落了一份旧 `dsh-tools` → `tools` 行被判
  不兼容并被禁用 → 所有 inject `tools` 的插件（`agent-loop`、`tool-working-directory`、
  `spill-policy`、`mcp-resources`、`tool-agent-team`、`dsh-project-ledger` …）全部 pending。
- 用户修复：本地插件改 `peerDependencies: ">=0.2.0-rc.2 <0.3.0"` + 重装依赖 + 手动激活
  （`state.json` 的 `lastResult` = `reactivated-after-tools-bump-20261028`）。
- 关键教训：`verify:smoke` 全程用临时 `DSH_HOME`、不带第三方插件，**永远抓不到这一类**。

## 二、本轮改动（代码）

  - `updateToLatest()` 在 `smokeTest` 之后、`activate` 之前插入 `profile-precheck` 阶段；

## 五、追加（2026-10-29 01:10，**结论已更正**）：问题不在中文路径，在「产物位于 agent 工作区内」

现象：双击 `产出\win-unpacked\DS Harness Desktop.exe`，**完全没反应**（连错误页都没有）。

先说被证伪的第一个猜测：最早以为是 `产出` 这个中文目录名让 Electron 秒退。**错。**
把同一份产物改名到纯英文目录后仍然失败，所以又做了一次严格的 A/B：

| 同一份产物放在哪 | 路径特征 | 结果 |
| --- | --- | --- |
| `G:\ai\dist-outside-test\`（工作区**外**） | 纯英文 | **正常启动**（并弹出「已有实例在运行」） |
| `G:\…\ds-harness-desktop\dist-internal-test\`（工作区**内**） | 纯英文、短 | 秒退 `0x80000003`（`STATUS_BREAKPOINT`，Chromium 沙箱初始化失败） |
| `G:\…\deepseek harness output\workspace\projects\ds-harness-desktop\产出\win-unpacked\`（工作区内） | 含中文 | 同上秒退 |

结论：**决定因素是 exe 是否位于 agent 会话工作区内**，与中文无关。工作区内的 Electron 进程
在跑我们的 JS 之前就被 Chromium 沙箱初始化失败带走了 → 表现为「双击没反应」、无窗口、无日志。
这与 `NEXT.md` 里那条旧坑一致（「凡镜像位于会话工作区内的进程…」），不是产物缺陷；安装版在
`G:\ai\dsh desktop`（工作区外）一直正常。

因此：
- 把 `directories.output` 从 `../产出` 改成 `../dist` **已做**（2026-10-29，顺带去掉中文名，
  顺手也更清晰），但它**不能**解决「双击没反应」——`dist\win-unpacked` 仍在工作区内；
- 本地要双击验证解压版，必须**把 `win-unpacked` 复制到工作区外**再点
  （本次用 `G:\ai\dist-outside-test`）；或加 `--no-sandbox` 启动；
- 已知坑应记成：「工作区内的 Electron 产物双击秒退 0x80000003，验证时复制到工作区外」，
  别再写成中文路径。

## 六、追加（2026-10-29 02:20）：**根因定位 = 工作区被标成 Low integrity（低完整性级别）**

上面第五节只描述了现象（"工作区内的产物起不来"），真正的机制在这里。

`icacls` 对比同一份产物：

| 文件 | 完整性标签 |
| --- | --- |
| `…\ds-harness-desktop\dist\win-unpacked\DS Harness Desktop.exe`（起不来） | `Mandatory Label\Low Mandatory Level:(I)(NW)` |
| `G:\ai\dsh-unpacked-test\DS Harness Desktop.exe`（能起） | 无标签（= Medium） |

再看目录链：只有**会话工作区根** `…\projects\ds-harness-desktop` 带
`Mandatory Label\Low Mandatory Level:(OI)(CI)(NW)`，上级 `G:\ai\…` 全是 Medium。

机制：agent 会话（含它派生的一切进程、构建、写文件）都在 Low 完整性级别下运行，
**目录上的 Low 标签会被新文件继承** → 所有在工作区里构建出来的 exe 都是 Low。

后果正好对上两种症状：
- **Electron 产物**：Low 进程无法初始化 Chromium 沙箱 → 启动即 `0x80000003`（STATUS_BREAKPOINT），
  连我们的 JS 都没跑，所以既没窗口也没日志；
- **NSIS 安装包**：Low 进程不能写 Medium 的 `%TEMP%` → `Error writing temporary file`。

为什么工作区外的副本能用：robocopy / 复制**不带完整性标签**，落盘就是 Medium。

修复（已实测）：把产物的完整性级别重置回 Medium 就能直接双击运行：

```powershell
# 普通 PowerShell 里跑（不要用 agent 会话，agent 自己是 Low，改不动 Medium）
icacls "…\ds-harness-desktop\dist" /setintegritylevel Medium /T /C
```

实测：重置后再从正常进程启动 `dist\win-unpacked\DS Harness Desktop.exe` →
启动成功，并在 `dsh-desktop.log` 里留下
`[single-instance] 收到另一个实例的启动请求；对方入口 = …\dist\win-unpacked\…`。

配套改动：
- 仓库根新增 `unlock-artifacts.cmd`：双击即把 `dist\` 重置为 Medium（普通双击 = Medium，有权改标签）；
- `AGENTS.md` 硬约束新增第 9 条（每次重新打包都要再跑一次，新文件会重新继承 Low）。
