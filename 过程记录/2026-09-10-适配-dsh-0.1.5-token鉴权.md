# 2026-09-10 适配 dsh 0.1.5-rc.1 的 token 鉴权

## 背景

用户插件升级后 harness 启动即闪退，根因是 `@nanmicoder/dsh-auto-mode@0.1.7`
只接受 harness `0.1.2-rc.1`，而运行时是 `0.1.1-rc.2`（插件硬校验不通过，
插件树加载失败、进程退出）。排查同时确认插件生态已分裂：

- `@nanmicoder/dsh-auto-mode` 最新 0.1.7 → 仅 `0.1.2-rc.1`
- `@linxin666/dsh-web-all` 最新 0.3.20 → 声明 `engines.dsh >= 0.1.5-rc.1`
- `@linxin666/dsh-web-ui-all`（旧名）没有任何版本适配 0.1.2-rc.1

因此选择「全最新」路线：harness `0.1.5-rc.1` + 插件全部最新，
auto-mode 暂时从 profile bundles 移除（保留依赖，待其跟进后恢复）。

## 上游行为变化（0.1.5-rc.1）

本地 Web UI 强制**进程级 token 鉴权**：`dsh web` 启动时在 stdout 打印
`http://127.0.0.1:<port>/?token=…`，首次带 token 访问会换取签名 cookie
（`dsh-auth-…`），之后裸地址才可访问。直接访问裸地址得到 401/404。

## 桌面端改动（app/src/main.js）

1. spawn dsh 时把 stdout/stderr 改为管道，原样 tee 到 `dsh-child.log`，
   同时从中解析带 token 的启动地址（`captureLaunchUrl`）。
2. 新增 `waitForLaunchUrl`：等到 token 地址再 `loadURL`，加载后 cookie 落盘，
   后续启动可复用。老版本 dsh 不打 token 地址时，退回原有「就绪即加载」逻辑。
3. `probeDsh` 换成 `probeExistingInstance`：用 Electron 会话（带历史 cookie）
   探测端口，区分 `ok` / `auth-required`；若已有实例要求 token 且本应用无有效
   cookie，则显示错误页提示用带 token 的地址在浏览器打开，而不是白屏 401。
4. 版本号 0.1.1 → 0.2.0；内置 `@deepseek-ai/dsh` 0.1.1-rc.2 → 0.1.5-rc.1。

## 验证

- 打包守卫通过：`bundled @deepseek-ai/dsh=0.1.5-rc.1, declared=0.1.5-rc.1`
- 冒烟测试（win-unpacked）：日志依次出现 `captured token launch url` →
  `waitForLaunchUrl result= token-url` → `loaded web UI (token)` → `bootstrap done`；
  清理后端口释放。
- 另在 CLI 侧验证：带 token 首次访问返回 HTTP 200（36710 字节）并下发
  `dsh-auth-…` cookie。

## 遗留 / 注意

- `@nanmicoder/dsh-auto-mode` 未启用，`permission.defaultPreset` 已从 `auto`
  退回内置 `workspace-write`；待 auto-mode 支持 0.1.5 后可装回并把默认值改回 `auto`。
- 旧版 Web 启动脚本（`start-deepseek-harness.bat`）里自行打开裸地址的逻辑已失效，
  应删掉该行，交给 `dsh web` 自己打开带 token 的地址。
